# Performance, connectivity and memory audit (2026-10-11)

Four read-only code audits (render, BLE, memory, main thread/audio/network) plus live
measurements on the Nubia. Commit 6d7211e applied the low-risk batch; the rest is below.

## Measured on the phone

- Idle CPU around 4–5 % of one core (2.5–3.1 s per minute), mostly BLE traffic.
- Render-to-display p50 192 ms, p90 277 ms. JS paint is ~10 ms; the rest is the send
  queue: 113 of the waits were "queued behind resource command", and Kotlin planning
  (pack → queued) took 30–130 ms even for 1-byte (unchanged) updates.
- Wake (compositor:unblank) ~300 ms: brightness, six resource commands (one ~5 KB),
  then the image.
- Passive ALS lease re-sent every 2 s, plus ~3 ALS notifications/s; heartbeat every 4.1 s.
- Heartbeats stay regular with the phone dozing and the wake lock released (the ALS
  stream keeps the CPU awake), so the wake-lock risk below did not show up here.
- Memory: PSS ~240 MB, no runaway growth found in code.

## Done in 6d7211e

- Mic PCM: bulk copy through a reused direct buffer both ways (was one JNI call per
  byte, ~30 ms/s of main thread while listening); no copy when nothing consumes it.
- fitLine binary search; wrapCapped stops at max+1 lines (chat painters were O(n²)).
- In-process windows coalesce requestRender bursts.
- Live facts: Brave hedge after 1 s of Perplexity; writer skipped for overtaken sentences.
- Wear bridge disables itself on API_NOT_CONNECTED (was logging stack traces).
- Paseo worker summaries capped at 500 and cleared on stop; Nightscout font at paint;
  firmware download via downloadBinary.

## Connectivity (second commit)

Done and measured on the Nubia:
- Bluetooth off then on: reconnected 1.5 s after the adapter came back. Before, the
  bond check read BOND_NONE with the adapter off and parked the session as "unpaired"
  for good (found while testing); isBonded now answers "unknown = bonded" while off,
  and an ACTION_STATE_CHANGED receiver skips the remaining backoff.
- Connect settle 800 → 300 ms; security auth still acks on both arms (~25 ms).
- MTU negotiates 247 on both arms (now logged under FaceclawBle, which the phone filters
  to warnings unless `setprop log.tag.FaceclawBle VERBOSE`).
- Wake calls (resume, await-ready) run on a Kotlin thread and answer through
  FaceclawBooleanResultListener; the JS queue still orders them, the main thread is free.

Done, needs a physical test:
- Leaving the charger reruns the connect sequence on the live links (no GATT teardown,
  no backoff); charging poll 30 → 10 s.
- Backoff 2/6/10 s → 2/6 s (the 6 s step still outlasts Android's ~4 s LE link linger).

Still open:
- Wake lock tied to the glasses screen (not seen in practice: ALS traffic keeps the CPU up).
- `writeCharacteristic(..., writeType)` lacks an API 33 guard (only matters below Android 13).
- GATT 133 quick retry; autoConnect during backoff gaps.
- After an app reinstall the arms can take 20–45 s to accept a new GATT client (stack-side
  encryption/L2CAP churn seen in logcat), independent of these changes.
